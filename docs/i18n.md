# Internationalisation

## Locales

English (default), French, and German (`context/constants.ts`) — chosen for
this UK creative agency's client base, not cbf-rebuild's six (that set was
chosen for a Tanzanian bank foundation's audience and doesn't transfer
here). The routing/translation infrastructure below is otherwise
language-count-agnostic; adding a fourth locale is a matter of adding it to
`context/constants.ts`, adding a dictionary JSON file, and adding it to
`i18n/dictionaries.ts`'s loader map.

## Locale routing

Every route lives under `app/[locale]/`. `proxy.ts` is what gets a visitor
there:

- A request whose pathname already starts with a supported locale segment
  (`/en`, `/fr/about`, …) passes through unchanged (aside from the CSP nonce
  — see [docs/security.md](./security.md)).
- Anything else is 307-redirected to the same path prefixed with a locale,
  resolved **cookie-first** (`NEXT_LOCALE`, set by `LocaleSwitcher.tsx` on
  every explicit choice), then the `Accept-Language` header (a hand-rolled
  parser — no BCP-47 library needed for three flat locale codes), then
  `defaultLocale`.

The matcher explicitly excludes `_next`, `/api`, and any path with a file
extension — an extension-less `/api` route (`/api/media/2025/01/hero.jpg`
has one, but a hypothetical extension-less API path wouldn't) has no `.` for
the second clause to catch, so without the explicit `api` exclusion it would
307 to a route that doesn't exist. This exact class of bug is what
`e2e/routing-i18n.spec.ts`'s "an extension-less /api route is never
locale-redirected" test guards against.

`getLocale`/`next/root-params`: unlike cbf-rebuild's reference
implementation, this project does **not** use `next/root-params` to read the
locale in deep server-side utilities — every translation helper
(`i18n/translateContent.ts`) takes `locale` as an explicit argument instead,
threaded down from each page/layout's own `params`. This app's route tree
is small enough (two page shapes) that prop-drilling is simpler than an
experimental Next.js API, and it keeps every helper trivially testable
without stubbing that API under Vitest.

## Static UI dictionary

`i18n/dictionaries/{en,fr,de}.json` + `i18n/dictionaries.ts`'s `getDictionary()`
cover fixed, non-CMS UI chrome — currently just the cookie-consent banner
and the locale-switcher label. `en.json` is the type source of truth
(`IDictionary = typeof en`); every other locale file is checked against that
same shape at import time. `getDictionary()` falls back to English for an
unrecognized locale rather than throwing.

## Azure Translator pipeline

`api/Translation/GetTranslatedContent.ts` is the raw Azure AI Translator
REST client — batches up to 100 strings per call, retries a `429`/`503` a
few times with backoff, and is never called for the default locale.
`i18n/translateContent.ts` wraps it with the shapes each caller actually
needs:

| Function | Used for |
|---|---|
| `translateFields` | A page's SEO fields (title/description/OG) |
| `translateUiStrings` | Fixed labels a block renders itself |
| `translatePostSummaries` | `title`/`excerpt` across a list (built, not yet wired to a live consumer — see [architecture.md](./architecture.md#known-gaps-carried-over-from-the-upgrade-plan-audit)) |
| `translateGlobalChrome` | Every menu label + theme-options prose, in exactly two Azure calls total |
| `translateBlockProse` / `translateFlexibleContent` | A page's flexible-content blocks, via the `PROSE_FIELDS` allowlist |

**`PROSE_FIELDS`** (in `i18n/translateContent.ts`) is a per-block-type
allowlist of which ACF fields are genuine translatable prose — built from
each block's own `types/<name>.ts` shape, not a blind "translate every
string" walk of untyped CMS data (which risks mistranslating a CSS class, a
URL, or a field name). `OurServices.service[].options[].text` — a repeater
nested inside another repeater row — isn't covered; the walker only
descends one repeater level, a deliberate scoping gap, not an oversight.

**Fail-soft, everywhere**: every translation function catches any Azure
error (missing credentials, rate limit, network failure) and returns the
English source unchanged, logging a `console.warn`. Verified live in this
upgrade session — with no Azure credentials configured, `/fr` and `/de`
both render correctly with English content rather than erroring.

## Canonical URLs and hreflang

`i18n/buildAlternates.ts`'s `buildLocaleAlternates(locale, pathWithoutLocale)`
builds both the `alternates.canonical` value and the full `hreflang`
`languages` map (one entry per locale, plus `x-default` pointing at the
un-prefixed English URL) from `SITE_URL` — never from the CMS's own
`seo.canonical`/`seo.opengraphUrl`, which have no locale segment and are
absolute URLs on the CMS's own origin (see
[docs/security.md](./security.md#cms-origin-masking)). `app/sitemap.ts`
uses the same helper to emit one `<url>` entry per page per locale, each
carrying the full set of `hreflang` alternates.

## LocaleSwitcher

`components/Global/LocaleSwitcher/LocaleSwitcher.tsx` — a Navbar dropdown
listing every supported locale (native-language label, no flag icons —
sourcing/designing flag assets wasn't something to invent unprompted).
Choosing one sets the `NEXT_LOCALE` cookie and navigates to the same page
under the new locale prefix.
